# Kaelis 性能基线报告 (B-3)

## 测试环境

| 项目 | 配置 |
|------|------|
| **测试时间** | 2026-04-29 |
| **后端** | Flask + Waitress (Python 3.14) |
| **数据库** | SQLite (WAL 模式) + ChromaDB (ONNX 禁用) |
| **Waitress 线程** | `max(4, min(8, CPU核心数))` |
| **SQLite 连接池** | 已启用 (max=8, WAL 模式, PRAGMA synchronous=NORMAL) |
| **测试工具** | `scripts/benchmark_load.py` |

## B-3 关键优化

### 1. 连接池 Commit Bug 修复 (CRITICAL)
- **问题**: `memory_manager_v2.py` 所有写入方法在 `POOL_AVAILABLE=True` 时**未调用 `conn.commit()`**，导致未提交写事务长期持有 WAL 写锁，阻塞后续写入 30 秒。
- **修复**: 移除 `if not POOL_AVAILABLE` 条件，写入后**无条件 commit**。
- **效果**: 写入延迟从 ~32000ms 降至 ~20ms。

### 2. FTS5 搜索连接池化
- **问题**: `core/memory_fts.py` 每次搜索都创建新的 `sqlite3.connect()`，高并发下连接开销大。
- **修复**: `MemoryFTS.search()` 优先复用 `core/db_pool.py` 连接池。
- **效果**: 搜索并发性能提升约 2~3 倍。

### 3. Waitress 线程数上限封顶
- **问题**: 默认 `CPU * 2`（本机 24 线程）导致 Python GIL 竞争，上下文切换开销大。
- **修复**: 默认线程数改为 `max(4, min(8, CPU))`。
- **效果**: 10 并发搜索 P95 从 >500ms 降至 ~250ms。

### 4. 基准测试模式
- 新增 `BENCHMARK_MODE=1` 环境变量，跳过中间件安全/限流检查，便于裸性能测量。

## 性能瓶颈分析

1. **Python GIL**: SQLite FTS5 查询是 CPU 密集型，Python GIL 使多线程无法真正并行，高并发下请求串行排队。
2. **SQLite 单文件架构**: WAL 模式支持多读者并发，但 FTS5 的 `JOIN` 查询在单文件上仍有 I/O 串行瓶颈。
3. **连接池上限**: 8 连接在 50 并发下成为瓶颈，但提高上限对 SQLite 单文件帮助有限。

## 结论与建议

| 并发度 | 记忆搜索 P95 | 状态 |
|--------|-------------|------|
| 5 | 102.9ms | ✅ 通过 |
| 10 | 269.7ms | ⚠️ 未通过 |
| 50 | 635.3ms | ⚠️ 未通过 |

**单机 SQLite 架构下，建议生产并发控制在 5~8 以内。**

如需支撑更高并发，后续优化方向：
1. **缓存层**: 对高频搜索增加 `functools.lru_cache` 或 Redis 缓存（命中率预期 >80%）。
2. **读写分离**: 搜索走只读副本或内存缓存，写入走主库。
3. **数据库迁移**: 迁移至 **PostgreSQL + pg_trgm** 或 **Meilisearch**，可支撑 100+ 并发搜索 < 50ms。
