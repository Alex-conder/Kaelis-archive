# 反常识战略演练 — 2026 Q2

**演练日期**: 2026-04-29
**假设提出**: 生态与整合架构师
**下次演练**: 2026-07-01

---

## 假设

> **Kaelis 不再自研任何 UI，所有交互通过 MCP Tool 由 Claude/ChatGPT 原生界面完成。**

---

## 推演分析

### 如果采纳，会发生什么？

#### 正面影响
| 维度 | 影响 |
|------|------|
| 开发成本 | 前端团队可缩减 80%，无需维护 React/Vite/Tailwind 栈 |
| 功能交付速度 | 新功能只需暴露 MCP Tool，无需设计 UI |
| 跨平台 | 自动获得 Claude Desktop、Cursor、VSCode Copilot 等所有 MCP 客户端支持 |
| 用户触达 | 潜在用户基数从"安装 Kaelis 的人"扩展到"所有 Claude 用户" |

#### 负面影响
| 维度 | 影响 |
|------|------|
| 品牌独立性 | Kaelis 退化为"后台服务"，用户感知的是 Claude，而非 Kaelis |
| 体验控制权 | 无法定制交互流程、视觉风格、动画反馈 |
| 离线能力 | 完全依赖云端 LLM，本地优先的核心价值被削弱 |
| 商业模式 | 难以建立独立的品牌付费墙，可能沦为开源基础设施 |
| 技术债转移 | MCP 协议的任何变动都会直接冲击用户体验，无缓冲层 |

#### 不可逆后果
- 现有用户（已习惯 Kaelis Web UI）面临强制迁移
- 前端代码库（~15k 行 TSX）成为沉没成本
- 设计系统和组件库投资全部作废

## 委员会投票

| 角色 | 投票 | 理由 |
|------|------|------|
| 首席架构师 | ❌ 放弃 | 丧失架构自主性，MCP 协议的演化不由我们控制 |
| 安全与合规官 | ❌ 放弃 | 所有数据流经第三方 LLM，本地隐私合规优势丧失 |
| 性能与可靠性工程师 | ❌ 放弃 | 延迟完全取决于外部服务，无法优化 |
| 测试与 QA | ⚠️ 观望 | 可减少前端测试负担，但需保证 MCP 接口稳定性 |
| UX 与设计 | ❌ 放弃 | 品牌体验完全不可控，设计系统投资作废 |
| 产品与市场 | ⚠️ 观望 | 触达扩大，但品牌稀释风险极高 |
| 技术文档与社区 | ❌ 放弃 | 贡献者体验受损，无法通过 UI 展示项目价值 |
| DevOps | ✅ 采纳 | 大幅减少 CI/CD 和部署复杂度 |
| 生态与整合架构师 | ⚠️ 观望 | 与我们的"生态整合"定位看似一致，但过度依赖单一生态是新的脆弱性 |

**结论**: **放弃**（5 反对，1 采纳，3 观望）

## 从假设中提取的洞察

虽然假设本身被否决，但推演中发现了若干值得采纳的**子策略**：

### 洞察 1: MCP-first 开发流程
即使保留 UI，新功能应**先暴露 MCP Tool，再开发 UI**。这样：
- 获得双重接口（REST + MCP）
- 为未来的第三方集成预留能力
- 减少对前端资源的阻塞

### 洞察 2: UI 轻量化
当前前端代码量（~15k 行）对于记忆中枢工具是否过度？
**建议**: 在 v0.4.0 中评估将部分管理界面（如 ApprovalModal、ToolsPage）降级为更轻量的实现（如基于 htmx 或纯 SSR）。

### 洞察 3: 品牌展示层
如果用户可能在 Claude 中使用 Kaelis，我们需要在 MCP 响应中**嵌入品牌标识**（如签名、版本信息、文档链接）。
**建议**: 所有 MCP Tool 返回的 JSON 中包含 `{"_kaelis_version": "0.3.x", "_docs": "..."}`。
